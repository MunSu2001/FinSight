1. 목적과 후보

이 평가는 모델 지식만 비교하지 않는다. raw exact + fuzzy + 재질문 + NOT_FOUND에 LLM 검색어 가설을 결합했을 때, 후보 생성과 상태 결정이 함께 안전하게 동작하는지 확인했다. LLM은 검색어만 제안하고, LLM이 추가한 후보는 항상 NEEDS_CONFIRMATION으로 보낸다.

후보정책
A. deterministic고유 raw exact는 자동 확정, 그 외 fuzzy 후보와 cutoff 75로 NEEDS_CONFIRMATION 또는 NOT_FOUND를 결정
B. local LLM expansionA와 동일한 상태 규칙에, 미해결 입력의 Qwen 검색어 가설과 OpenDART 재검증 후보를 추가

3. 사례별 해석

B의 실제 회수: A는 삼성에스디아이와 에스케이이노베이션에서 정답 후보를 만들지 못했다. B는 각각 삼성SDI, SK이노베이션을 제안하고 OpenDART에서 검증해 후보에 포함했다. 두 사례 모두 자동 확정하지 않고 사용자 확인 상태를 유지했다.

후보 수 증가: 대한항콩은 5개에서 13개, 에스케이이노베이션은 5개에서 15개 후보로 늘었다. 정답 회수에는 도움이 되지만, UX에서는 후보 정렬·표시 개수 정책을 별도로 정해야 한다.

미등록명 주입: 한화오션솔루션즈는 현재 OpenDART의 등록 법인명이 아닌데, B는 한화오션솔루션즈와 한화오션을 검색어로 제안했다. 한화오션은 실제 법인이므로 후보에 들어갔다. 현재 정책은 자동 확정을 금지해 잘못된 데이터 조회를 막았지만, 사용자는 불필요한 확인을 받게 된다.

cutoff 한계: 이 미등록명은 fuzzy 최고점이 cutoff 75 이상이어서 A도 재질문으로 보냈다. 따라서 이 결과는 ‘LLM만의 문제’가 아니라, 실제 기업명과 매우 비슷한 미등록명을 cutoff 하나로 NOT_FOUND와 구분하기 어렵다는 근거다.

4. 채택·미채택 판단

조건부 유지: B. local LLM expansion 정책 구조
B는 Candidate Recall과 LLM 신규 기여를 높였고, 자동 오선택·False Not-found Rate를 높이지 않았다. 따라서 LLM 검색어를 OpenDART 검증 후보에만 추가하고 자동 확정하지 않는 구조는 다음 API holdout에서 검증할 가치가 있다.

미채택: A. deterministic 단독 정책
A는 빠르고 자동 선택도 안전했지만, 한글 음역 두 건에서 정답 후보를 놓쳤다. 기업명 변형을 후보 단계에서 회수하는 역할로는 부족하다.

최종 정책 선정 보류: B의 no-target 후보 주입, 양 후보의 Not-found Recall 0.750, 후보 수 증가가 남아 있다. 이 개발용 로컬 validation만으로 운영 정책·cutoff·후보 표시 UX를 확정하지 않는다. 변경하지 않은 정책을 운영 후보 OpenAI API로 독립 holdout에서 1회 검증한다.

5. 한계

  • 이 사례는 입력 문자열을 이전 평가와 구분한 개발용 validation이며, 독립 holdout이 아니다. 결과를 본 뒤 Prompt·cutoff를 조정하면 새 holdout이 필요하다.
  • 로컬 Qwen의 결과는 OpenAI API 운영 모델의 품질 근거가 아니다. API holdout에서 동일 정책을 별도로 확인해야 한다.
  • 후보는 fuzzy와 LLM의 서로 다른 점수 체계를 합쳐 보여 준다. 현재 후보 수만 측정했으며, 후보 정렬이나 상위 K 사용자 경험은 아직 평가하지 않았다.
  • 자동 확정 뒤의 실제 사용자 선택은 오프라인 평가에 없으므로, 사용자 확인 후 최종 Entity Accuracy를 이 결과에서 측정하지 않았다.
