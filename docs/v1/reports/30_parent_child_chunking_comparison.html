테스트 목적: 검색 방식을 E5 + Kiwi BM25, RRF 5:5로 고정한 상태에서 청킹과 부모 문맥 반환 방식이 근거 회수에 미치는 영향을 비교한다. 작은 검색 단위에서 근거를 찾는 성능뿐 아니라, 부모로 확장한 근거를 동일한 문맥 예산 안에 담을 수 있는지도 확인한다. LLM 답변 품질이나 구조화 SQL 검색을 평가한 실험은 아니다.
간단한 결과: A는 예산 적용 후 Hit@5 26/30(86.7%), 근거 Recall 0.8333으로 전체 근거 회수가 가장 높았다. B는 각각 23/30(76.7%), 0.7500이지만, 복합 질문 Recall은 A보다 높았다(0.70 대 0.60). C는 확장 문맥에 모든 정답 근거가 있었으나, 첫 문맥부터 2,400토큰을 넘어서 전부 반환되지 않았다. C의 예산 점수 0은 제목 계층 검색 자체의 실패가 아니라 현재 부모 반환·예산 정책의 결과다. A를 다음 평가 기준선으로 유지할 것을 권장하며, 최종 운영 구조는 확정하지 않는다.

가설은 부모 확장이 작은 청크의 경계 밖에 있는 근거를 보완한다는 것이다. 반대로 너무 큰 부모는 관련 없는 내용을 함께 늘리고, 한정된 입력 예산에서 뒤쪽 근거를 밀어낼 수 있다. 이번 실험은 청킹 경계와 반환 정책을 함께 비교하므로, 결과 차이를 부모 확장 하나의 효과로만 해석하지 않는다.

Hit는 알려진 정답 근거가 하나라도 포함된 질문의 비율이다. MRR은 처음 정답 근거가 나온 검색 순위의 역수 평균이다. 근거 Recall은 질문별로 찾은 정답 근거 ID 수 / 필요한 정답 근거 ID 수를 계산한 뒤 30개 질문을 평균한다. 예를 들어 복합 질문에서 두 근거 중 하나만 찾으면 Hit는 1, Recall은 0.5다.

문맥 지표는 검색 상위 5개에서 시작해 확장·중복 제거·예산 적용한 결과를 대상으로 한다. 실제 반환 문맥이 반드시 5개라는 뜻은 아니다. 이전 29번의 청크 수 기반 Recall과 이번의 고정 근거 ID 기반 Recall은 분모가 다르므로 직접 비교하지 않는다. 또한 문서의 의미상 관련 근거를 전부 주석화한 Recall이나 LLM의 정확도·할루시네이션 지표가 아니다.

A는 전체 예산 내 근거 회수가 가장 높고, B는 검색 MRR이 가장 높다. 즉 B가 처음 찾은 근거의 순위는 평균적으로 더 좋지만, 충분한 근거를 전달한 질문 수는 A가 많다. 순위와 누락률은 같은 성능이 아니다.

4. C의 0점을 어떻게 해석해야 하는가

C는 작은 검색 단위에서 26/30문항에 적중했고, 실제 제목 부모로 확장하면 30/30문항의 모든 정답 인용문이 들어 있었다. 그러나 첫 반환 단위부터 2,400토큰을 넘어서 현재 packing 규칙이 즉시 중단했다. 결과적으로 실제 전달 예정 문맥은 30문항 모두 비어 있었다.

예산 전 반환 문맥의 중앙값은 36,889토큰이고 NAVER 복합 질문 M_N은 합계 908,791토큰이다. 이 합계는 서로 다른 부모 사이의 겹치는 내용도 포함할 수 있어 문서의 고유 텍스트 길이가 아니다. 넓은 장 전체를 포함하면 정답 포함률은 높아지지만, 정확하게 좁힌 근거라고 보기는 어렵다.

따라서 “제목 계층 청킹은 성능이 나쁘다”는 결론은 낼 수 없다. 확인된 문제는 “큰 제목 부모를 통째로 반환 + 2,400토큰 예산 + 초과 시 즉시 중단”의 조합이다. 제목 구조 보존과 실제 입력 문맥을 조립하는 정책을 구분해야 한다. 부모 깊이 제한, 근거 주변 문맥 반환 등은 가능한 후속 후보이며 이번에는 구현하거나 검증하지 않았다.

반대로 예산 전 Recall 100%만 보고 C를 채택하는 것도 적절하지 않다. 필요한 근거가 넓은 문맥 어딘가에 있다는 사실과, LLM이 읽을 수 있는 제한된 입력 안에 그 근거가 있다는 사실은 다르다. 2,400은 이번 비교에서 고정한 E5 토큰 예산이며 최종 운영 모델의 확정 입력 한도가 아니다.

비용 해석: LLM·OpenAI 임베딩 호출이 없으므로 이 실험의 해당 API 호출 요금은 발생하지 않았다. 로컬 CPU·RAM·전력 비용과 OpenDART 호출 한도 소비는 별개이며 금액으로 측정하지 않았다. E5 파라미터 크기 약 448.81MiB는 모델 파라미터만의 값으로 실행 전체 RAM이나 VRAM 사용량이 아니다. GPU를 사용하지 않았으므로 VRAM 측정 결과는 없다.

속도 해석: B/C의 E5 구성 시간이 짧은 주원인은 앞선 후보에서 만든 동일 텍스트 임베딩을 재사용했기 때문이다. C가 독립적인 처음 실행에서 1초 만에 임베딩된다는 뜻이 아니다. 검색 시간은 준비된 색인을 대상으로 한 구간 측정이며 XML 다운로드·모델 로드·LLM 생성이 포함된 사용자 전체 지연시간이 아니다. 약 0.22초의 모델 로드도 콜드 스타트 벤치마크로 해석하지 않는다.

토큰은 E5 기준이라 운영 LLM의 토큰 수·입력 요금과 직접 같지 않다. 다만 C의 큰 문맥과 겹치는 부모 내용은 문맥 조립·저장 공간의 부담이 관측됐다는 근거다. 이번 선택에서는 미세한 검색 지연시간보다 근거 회수와 예산 내 전달을 우선한다.

9. 한계와 재현 근거

  • 5기업·2024년 사업보고서 5개와 30개 개발 질문만 평가했다. 다른 연도·기업·실제 사용자 질문 전체로 일반화하지 않는다.
  • 복합 질문은 5개로 적다. 지표 차이에 대한 통계적 유의성·독립 holdout·LLM 답변 평가는 수행하지 않았다.
  • 정답은 고정 인용문 포함 여부로 판정한다. 같은 의미의 다른 표현이나 문서의 모든 관련 근거를 완전하게 주석화하지 않았다.
  • 같은 예산을 사용했지만 부모 전체를 통째로 넣는 packing은 큰 문맥에 불리하다. 청킹·반환·예산 정책의 결합 결과로 해석한다.
  • 정답 보존 확인과 오류 출력 0건은 XML 본문 전체의 무손실 추출을 증명하지 않는다.
  • 저장된 실행 로그의 90개 기록으로 Hit·Recall·예산 후 토큰·완전 근거 회수 수를 재계산해 저장 요약과 대조했다. MRR·시간은 저장 요약을 사용했다. 실행된 notebook 코드는 수정하거나 재실행하지 않았다.
