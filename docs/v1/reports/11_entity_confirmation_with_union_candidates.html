V1 기업 식별: 통합 후보 기반 확정·재질문 정책 비교

실행일: 2026-09-14. OpenDART 기업코드 레코드 119,183개와 정규화 이름 키 219,425개를 사용했다.

목적

10번에서 조건부 채택한 exact + fuzzy 통합 후보 생성기 위에서, 어떤 입력을 자동 확정하고 어떤 입력을 재질문해야 하는지 비교한다. LLM은 사용하지 않았으며, corp_code 선택과 상태 결정은 결정론적 정책으로만 평가했다.

평가 구성

  • 자동 확정 기대 14건: 정식명·띄어쓰기·검증된 별칭·명백한 오타
  • 재질문 기대 4건: 삼전, 엘지, 현대, 삼성
  • 별칭·오타 확정 시에는 해석 안내 문구가 함께 나와야 함
정책동작
A. 최상위 후보 자동 선택후보가 있으면 정렬상 첫 번째 법인을 바로 확정
B. 고유 exact만 자동 확정정규화 exact 법인이 하나일 때만 확정, 나머지는 재질문
C. 출처 기반 해석 확정고유 exact 또는 초기 검증 별칭·오타 정정만 확정. 정정 시 안내 문구를 반환하고, 동명·포괄 표현은 재질문

채택 판단

정책판정근거
A. 최상위 후보 자동 선택미채택재질문이 필요했던 4건을 모두 자동 선택했고, 전체 자동 선택의 44.4%가 안전하지 않았다.
B. 고유 exact만 자동 확정미채택A보다 안전하지만 삼성을 실제 동명 법인으로 자동 확정했다. 또한 별칭·오타 6건을 해석하지 못해 재질문으로 보냈다.
C. 출처 기반 해석 확정조건부 채택이번 개발 정책 사례에서 자동 확정 14/14, 해석 안내 6/6, 위험 자동 선택 0/14, 재질문 4/4를 만족했다. V1의 초기 기업 식별 정책 형태로 채택한다.
중요한 한계: C의 별칭·오타 정정 목록과 평가 사례는 같은 개발 정책에서 정의됐다. 따라서 1.000 점수는 미지 사용자 표현에 대한 일반화 성능이 아니라, 현재 정한 초기 규칙이 의도한 확정·안내·보류 흐름을 수행했음을 뜻한다. 서비스 운영 후 실제 사용자 입력·오선택·재질문 로그를 검토해 별칭·보류 목록을 갱신해야 한다.

운영 성능 해석

세 정책 모두 후보 생성에 exact + fuzzy 통합을 사용하므로 p50은 약 26ms로 비슷하다. C의 p95가 약 33ms인 것은 해석 확정 시 종목코드로 OpenDART 레코드를 찾는 notebook 구현 비용이 포함됐기 때문이다. 최종 구현 단계에서는 종목코드 인덱스로 바꿔야 하지만, 현재는 정책 선택 전의 notebook 실험이므로 최적화하지 않는다.

결론

V1 초기 정책은 C의 형태로 둔다. 즉 고유 exact → 확정, 명시적 별칭·오타 정정 → 해석 안내와 함께 확정, 동명·포괄 표현·근거 없는 fuzzy 후보 → 재질문이다. 다음에는 이 정책을 고정한 뒤, 존재하지 않는 기업명을 NOT_FOUND로 구분하는 cutoff 정책을 다시 평가한다.
