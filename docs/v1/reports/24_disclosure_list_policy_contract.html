24. 공시 목록 정책·데이터 계약 비교

실행일: 2026-10-02 · OpenDART 공시검색 API · 삼성전자·SK하이닉스·리노공업 · 접수일 2024-01-01~2024-12-31

목적: 공시 목록을 재무제표의 사업연도와 별개인 접수일 기간으로 조회할 때, 전체 제출본(last_reprt_at=N)과 최종보고서만(Y)의 결과 차이를 확인한다. 동시에 페이지 누락·다른 회사 혼입·범위 밖 접수일·잘못된 접수번호가 없는지 검사한다. 이 검사가 필요한 이유는 목록이 불완전하거나 이전 제출본을 최종본으로 오인하면 이후 원문 근거 선택도 흔들리기 때문이다.
간단한 결과: 세 기업 모두 Y 결과가 N의 부분집합이었다. 전체 445건 중 Y에는 417건이 남고 28건은 N에만 있었다. 6개 조회의 전 페이지·건수 계약은 모두 맞았다. V1의 기존 “최종본 중심 목록” 기본값 Y는 조건부 유지하되, 이를 “2024년에 접수된 모든 공시 이력”이라고 설명해서는 안 된다.

1. 비교 조건과 가설

항목고정 또는 비교 조건
기업·기간세 기업의 OpenDART corp_code, 동일 접수일 범위 20240101~20241231

가설Y는 N보다 적거나 같은 접수번호를 반환하고, 최종본 중심 화면에는 적합하다. 단, N에서만 보이는 과거 제출 이력을 잃으므로 “전체 접수 이력” 요청에는 적합하지 않을 수 있다.

주의: 여기서 2024년은 rcept_dt의 접수연도다. 2024 사업연도 보고서를 뜻하지 않는다. 공시의 중요도 판단, 본문 검색, LLM Tool 선택과 최종 답변은 이번 실험에 포함하지 않았다.

N에만 있는 접수번호의 보고서명에는 삼성전자 연결재무제표기준영업(잠정)실적(공정공시), SK하이닉스 [기재정정]증권신고서(채무증권), 리노공업 현금ㆍ현물배당결정 등이 보였다. 즉 N/Y 차이는 실제 결과에 존재한다. 다만 제목과 집합 차이만으로 개별 문서가 왜 제외됐는지, 어떤 정정 문서와 연결되는지는 검증하지 않았다.

가장 중요한 해석: Y의 28건 감소를 “불필요한 공시 28건 제거”라고 말할 수 없다. 공식 API의 최종보고서 필터가 적용된 결과일 뿐이다. 사용자가 특정 시점의 제출 이력·정정 과정을 조사하려면 N이 필요할 수 있다. 반대로 최종본만 보여 주려는 화면에서 N을 그대로 쓰면 여러 제출본을 현재 최종 근거처럼 혼동할 위험이 있다.

4. 호출 시간과 자원

N과 Y는 각각 6개 페이지 API 요청을 사용했다. 기록된 공시검색 API 응답시간 합은 N 약 934ms, Y 약 1,014ms(전체 약 1,948ms)이며, 페이지 요청 중앙값은 각각 약 154ms와 173ms다. 호출 수가 같고 단일 실행이므로 이 차이를 정책의 속도 우열로 해석하지 않는다. 기업코드 ZIP 조회 시간은 이 수치에 포함되지 않는다. LLM 호출·토큰 사용량은 0이고 RAM·CPU peak, OpenDART 과금액은 측정하지 않았다.

5. 채택·미채택과 남은 질문

정책V1 판단이유·조건
B. 최종보고서만(Y)기존 기본값 조건부 유지V1 요구사항의 최종본 중심 목록에 맞고, 이번 세 기업에서 Y는 N의 부분집합이었다. 결과 화면에 “최종보고서만”을 명시해야 한다. 문서별 정정 계보와 다른 기업·기간의 동작은 별도로 확인해야 한다.
A. 전체 제출본(N)기본값 미채택최종본 중심 화면에 이전 제출본까지 함께 노출한다. 다만 과거 접수 이력·정정 과정을 조사하는 요청에는 필요한 별도 모드일 수 있으므로 N 자체를 폐기하지 않는다.

이 판단은 V1의 기존 범위를 유지한 것이며, 사용자 요청에 따라 N 모드를 제공할지 여부는 이번 결과만으로 확정하지 않는다. 사업보고서 원문 RAG로 넘어갈 때는 목록의 rcept_no를 문서 선택에 어떻게 사용할지 별도 근거·평가가 필요하다.
