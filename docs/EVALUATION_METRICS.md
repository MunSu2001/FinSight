# FinSight 평가 지표 가이드

이 문서는 FinSight에서 사용하는 정량 평가 지표의 의미, 계산 기준, 해석 주의점을 기록하는 살아 있는 기준 문서다.

- 새 평가를 시작할 때 해당 지표의 **정답 데이터**, **분모**, **평가 단위**, **비교 후보**를 함께 기록한다.
- 모든 지표에 고정 합격선을 먼저 두지 않는다. 같은 평가셋에서 A/B 후보를 비교하고, 핵심 지표가 명확히 우세할 때만 채택한다.
- 하나의 지표만 좋아졌다고 최종 선택하지 않는다. 품질 지표가 충돌하면 실패 사례와 사용자 시나리오를 다시 확인한다.
- 지표의 정의는 프로젝트가 정한 운영 정의다. 표준 정보검색 지표는 일반적 정의를 따르되, 정답·관련성 판단 기준은 실험마다 명시한다.

## 1. 기업 식별(Entity Resolution)

사용자 기업명 표현을 올바른 OpenDART `corp_code`와 상장 종목코드로 연결하는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Entity Accuracy | 정답 기업으로 최종 선택한 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 높을수록 기업을 정확히 확정함 | `corp_code` 또는 종목코드를 정답으로 고정해야 함 |
| Candidate Recall | 정답 기업이 후보 집합에 포함된 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 낮으면 이후 ranking·사용자 확인으로도 복구 불가 | 후보에 순위가 없으면 현재 `Candidate Recall`, 순위가 있으면 `Recall@K`로 기록 |
| Candidate Recall@K | 정답 기업이 상위 K개 후보 안에 있는 사례 수 / 전체 정답 사례 수 | 후보를 K개만 보여 줄 UX의 상한 품질 | 후보 정렬 기준을 고정해야 함 |
| Coverage | 자동으로 기업 하나를 확정한 양성 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 높을수록 사용자 추가 선택이 적음 | 잘못 고른 결과를 숨길 수 있으므로 Accuracy와 함께 봄 |
| Unsafe Selection Rate | 자동 선택한 결과 중 오답 수 / 자동 선택한 전체 결과 수 | 낮을수록 안전함 | 0%라도 보류가 지나치게 많으면 Coverage가 낮을 수 있음 |
| 보류 정확도(Abstention Accuracy) | 존재하지 않거나 의도적으로 모호한 입력을 올바르게 보류한 수 / 보류가 정답인 사례 수 | 높을수록 임의 선택을 잘 피함 | 존재하지 않는 이름, 복수 상장 후보 등 보류 정답 사례가 필요 |

현재 `05_entity_resolution_baseline.ipynb`의 개발 결과는 별칭 규칙을 만든 사례를 다시 평가하므로 최종 성능이 아니다. 최종 비교 전에는 별칭 사전 작성에 쓰지 않은 holdout 사례가 필요하다.

## 2. OpenDART 데이터 계약과 정제

OpenDART raw 응답을 V1의 표준 재무 데이터로 안전하게 바꾸는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Field Accuracy | 정답 원천 계정·금액·통화가 맞게 매핑된 필드 수 / 검증 대상 필드 수 | 높을수록 재무 항목 매핑이 정확함 | `account_id`, `sj_div`, 원금액을 함께 정답으로 남김 |
| Statement-Basis Accuracy | 기대된 CFS/OFS 기준을 선택한 사례 수 / 재무조회 사례 수 | 높을수록 연결 우선·별도 대체 정책이 정확함 | CFS 일부 결측을 OFS 값으로 섞지 않는 정책을 별도 확인 |
| Missing-data Handling Accuracy | 결측·API 오류 사례에서 기대한 처리(결측 유지, 대체, 제한 표시)를 한 수 / 해당 사례 수 | 높을수록 없는 값을 임의 생성하지 않음 | 단순 성공률이 아니라 오류·결측 사례가 정답셋에 있어야 함 |
| Entity Eligibility Precision / Recall | 비금융 상장기업을 허용·제외한 결과의 Precision/Recall | V1 대상 범위 판정 품질 | 금융·보험, 비상장, 상장 예외 사례를 포함해야 함 |

## 3. 재무 계산

원천 재무값으로 성장률, 영업이익률, ROA, ROE, 부채비율 등을 계산하는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Calculation Accuracy | 정답 수식·단위·반올림 결과와 일치한 계산 수 / 계산 사례 수 | 높을수록 수식과 단위 처리가 정확함 | 계산 전 사용한 원천값과 수식을 함께 기록 |
| Unsafe-calculation Rate | 분모 0, 음수 자본, 결측 등 계산 불가 상황에서 부적절하게 숫자를 낸 수 / 위험 계산 사례 수 | 낮을수록 안전함 | `계산 불가` 또는 주의 문구가 정답인 사례가 필요 |
| Unit Consistency Rate | 비교·계산한 값의 통화·단위가 동일하게 정규화된 사례 수 / 계산 사례 수 | 높을수록 규모 오류가 적음 | 원화, 백만원, 억원 표현과 raw 원금액을 구분 |

## 4. Router·Tool 선택·인자 생성

LLM 또는 workflow가 질문을 분석해 필요한 Tool과 인자를 선택하는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Route Exact Match | 정답 workflow 경로와 실제 경로가 완전히 같은 사례 수 / 전체 사례 수 | 높을수록 분기 판단이 정확함 | 서로 다른 경로가 같은 정답을 낼 수 있으면 허용 경로를 명시 |
| Tool Precision | 호출한 Tool 중 실제로 필요한 Tool 수 / 호출한 Tool 수 | 낮으면 불필요한 호출·비용이 많음 | Tool 집합 기준으로 계산 |
| Tool Recall | 정답 Tool 중 실제로 호출한 Tool 수 / 정답 Tool 수 | 낮으면 필요한 조사 단계를 빠뜨림 | Tool 미호출이 최종 근거 누락으로 이어질 수 있음 |
| Tool F1 | Tool Precision과 Recall의 조화평균 | 둘 사이 균형을 한 값으로 봄 | Precision·Recall을 함께 보고 해석 |
| Argument Exact Match | Tool 인자(기업, 연도, 재무제표 기준 등)가 정답과 모두 일치한 호출 수 / 평가 호출 수 | 높을수록 올바른 데이터를 조회함 | 일부 인자만 중요한 경우 필드별 정확도를 추가 기록 |
| Over-call Rate | 정답에 없는 Tool 호출 수 / 전체 Tool 호출 수 | 낮을수록 불필요한 조사·비용이 적음 | 필요한 재검증 호출은 오류로 취급하지 않도록 정책 명시 |
| Invalid-plan Rate | 허용하지 않은 Tool 순서, 누락 인자, 지원 밖 요청 등 실행 불가능 계획 수 / 전체 계획 수 | 낮을수록 workflow가 안전함 | 구조화 출력 스키마 검증과 함께 사용 |

## 5. 문서 처리·Chunking·RAG

사업보고서 원문에서 근거 문단을 찾는 단계다. OpenDART 공시 목록 조회는 기간 필터 결과이므로 이 범주의 retrieval 지표를 적용하지 않는다.

### 5.1 문서 추출·OCR (필요한 경우만)

| 지표 | 의미와 계산 | 주의점 |
|---|---|---|
| CER (Character Error Rate) | 문자 편집 오류 수 / 정답 문자 수 | OCR 또는 텍스트 추출 결과에 정답 원문이 있을 때만 사용 |
| WER (Word Error Rate) | 단어 삽입·삭제·치환 오류 수 / 정답 단어 수 | 한국어 토큰화 기준을 실험마다 고정해야 함 |
| Table / Field Extraction Accuracy | 정답 표 셀·필드를 맞게 추출한 수 / 대상 셀·필드 수 | 표 구조가 중요한 재무·공시 데이터에 사용 |

### 5.2 Chunking

Chunking 방식 자체에 모든 상황에 통용되는 단일 점수는 없다. Chunk가 달라지면 이후 retrieval·citation 품질이 달라지므로 아래처럼 평가한다.

| 지표 | 의미와 계산 | 주의점 |
|---|---|---|
| Gold Span Coverage | 정답 근거 구간 전체가 하나 이상의 Chunk에 보존된 사례 수 / 근거 사례 수 | 문단·표가 부적절하게 잘렸는지 확인하는 프로젝트 정의 지표 |
| Context Preservation Rate | 필요한 제목·표 머리글·주변 문맥이 근거 Chunk에 함께 남은 사례 수 / 근거 사례 수 | 정답 기준을 사람이 먼저 정해야 함 |
| Downstream Retrieval Quality | 동일 retriever에서 Chunk 후보별 Recall@K, MRR, nDCG@K 비교 | Chunking은 이 downstream 지표와 지연시간으로 최종 선택 |

### 5.3 Retrieval·Reranking

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Recall@K | 상위 K개 문서/Chunk 안에 정답 근거가 하나 이상 있는 질의 수 / 전체 질의 수 | 낮으면 LLM이 정답 근거를 받을 기회가 없음 | K와 정답 근거 정의를 고정 |
| MRR | 각 질의의 첫 정답 근거 순위의 역수 평균 | 첫 정답이 위에 올수록 높음 | 여러 정답이 있어도 첫 정답 순위만 반영 |
| nDCG@K | 상위 K개 결과의 등급별 관련성과 순위를 할인해 계산한 점수 | 더 관련성 높은 근거를 위에 둘수록 높음 | 0/1 또는 등급형 relevance 기준을 정해야 함 |
| Citation Retrieval Recall | 최종 답변에 필요한 각 인용 근거가 검색 결과에 포함된 비율 | 근거 기반 답변 가능성을 측정 | 답변 단위의 필수 근거 목록이 필요 |
| Retrieval Latency | 질의부터 검색 결과 반환까지의 시간 | 낮을수록 응답성이 좋음 | 품질이 비열등한 후보 사이에서 비용과 함께 판단 |

## 6. LLM 답변·근거 검증

LLM이 Tool·RAG 결과를 바탕으로 최종 설명을 만드는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Numeric Faithfulness | 답변 속 수치·기간·계산이 Tool 원천 결과와 일치한 주장 수 / 수치 주장 수 | 높을수록 숫자 환각이 적음 | 반올림 허용 범위를 미리 정함 |
| Citation Correctness | 답변의 인용이 실제 해당 주장을 뒷받침한 수 / 인용 수 | 높을수록 근거 연결이 정확함 | 단순 링크 존재가 아니라 주장 지원 여부를 판정 |
| Claim Support Precision | 근거로 뒷받침되는 주장 수 / 전체 검증 가능 주장 수 | 높을수록 근거 없는 설명이 적음 | 주장 단위 분할 규칙 필요 |
| Unsupported Claim Rate | 근거가 없는 주장 수 / 전체 검증 가능 주장 수 | 낮을수록 좋음 | Claim Support Precision의 보완 지표 |
| Limitation Accuracy | 데이터 부재, OFS 대체, 비교 불가 등 제한을 올바르게 밝힌 사례 수 / 제한 표시가 필요한 사례 수 | 높을수록 과장·오해가 줄어듦 | 금융 분석에서는 특히 중요 |

## 7. Agent Workflow·통합 품질

검증된 Tool·RAG·Validator를 연결한 뒤 전체 요청을 처리하는 단계다.

| 지표 | 의미와 계산 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|
| Task Completion Rate | 최종 답변이 요청한 핵심 작업을 모두 마친 사례 수 / 전체 요청 수 | 높을수록 사용자 요청을 끝까지 처리함 | 단순 답변 생성이 아니라 필요한 조사·계산 완료가 기준 |
| Evidence-complete Task Rate | 핵심 결론과 수치에 필요한 출처·근거가 모두 있는 완료 사례 수 / 전체 요청 수 | 높을수록 evidence-first 원칙을 만족 | Completion Rate와 별도로 봄 |
| E2E Error / Partial-result Rate | 오류 또는 필수 결과 누락으로 부분 처리된 요청 수 / 전체 요청 수 | 낮을수록 안정적 | 오류, 사용자 확인 요청, 정상적인 제한 응답을 구분 |
| Agent Steps | 요청 한 건에서 실행한 node·Tool 호출 단계 수 | 불필요하게 높으면 지연·비용 증가 가능 | 품질이 같은 후보 사이에서만 단순화 근거로 사용 |

## 8. 운영 성능·자원 사용

품질이 명확히 열등하지 않은 후보 사이에서 비용과 운영 적합성을 비교하는 지표다.

| 지표 | 의미와 계산 | 주의점 |
|---|---|---|
| p50 Latency | 전체 요청 시간의 중앙값 | 일반적인 사용자 체감 속도 |
| p95 Latency | 전체 요청 중 느린 5%를 제외한 상위 지연시간 경계 | 느린 사례·외부 API 지연을 확인 |
| Cold Start Time | 모델·인덱스·데이터를 처음 로드해 첫 요청을 처리할 때까지 시간 | 로컬 모델·대시보드 운영에서 중요 |
| Warm Latency | 초기 로드 후 반복 요청 처리 시간 | Cold Start와 분리 기록 |
| Error Rate | 오류 응답 수 / 전체 요청 수 | timeout, API 오류, 파싱 오류를 원인별 기록 |
| Tool-call Count | 요청당 Tool 호출 수 | 불필요한 호출은 비용·지연 증가 요인 |
| VRAM / RAM Peak | 실행 중 최대 GPU·메모리 사용량 | 로컬 Qwen 모델과 RAG 인덱스 운영 가능성 판단 |
| Model / Index Size | 모델 파일·벡터 인덱스 등 저장공간 | 배포와 로딩 비용 판단 |

## 갱신 규칙

- 새 지표를 사용하기 전: 이 문서에 지표의 평가 대상, 분모·분자, 정답 단위, 해석 주의점을 추가한다.
- 실제 A/B 결과가 나온 뒤: `docs/<version>/reports/`에 데이터 기준일, 후보, 설정, 결과, 해석, 채택·보류 이유를 기록한다.
- 지표 이름은 같아도 정답 기준이나 분모가 달라지면 별도 실험으로 기록한다.
