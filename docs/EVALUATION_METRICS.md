# FinSight 평가 지표 가이드

이 문서는 FinSight에서 사용하는 정량 평가 지표의 의미, 계산 기준, 해석 주의점을 기록하는 살아 있는 기준 문서다.

- 새 평가를 시작할 때 해당 지표의 **정답 데이터**, **분모**, **평가 단위**, **비교 후보**를 함께 기록한다.
- 모든 지표에 고정 합격선을 먼저 두지 않는다. 같은 평가셋에서 A/B 후보를 비교하고, 핵심 지표가 명확히 우세할 때만 채택한다.
- 하나의 지표만 좋아졌다고 최종 선택하지 않는다. 품질 지표가 충돌하면 실패 사례와 사용자 시나리오를 다시 확인한다.
- 지표의 정의는 프로젝트가 정한 운영 정의다. 표준 정보검색 지표는 일반적 정의를 따르되, 정답·관련성 판단 기준은 실험마다 명시한다.

> 아래 예시는 지표의 분자·분모와 해석을 설명하기 위한 가상 사례다. 실제 실험 결과나 합격선이 아니다.

## 1. 기업 식별(Entity Resolution)

사용자 기업명 표현을 올바른 OpenDART `corp_code`와 상장 상태·종목코드(있는 경우)로 연결하는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Entity Accuracy | 정답 기업으로 최종 선택한 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 사용자 선택까지 끝난 10건 중 9건의 `corp_code`가 정답이면 0.9 | 높을수록 기업을 정확히 확정함 | `corp_code` 또는 종목코드를 정답으로 고정해야 함 |
| Auto-resolution Success Rate | 사용자 확인 없이 자동 확정했고 정답 기업까지 맞춘 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 정답 기업 10건 중 자동·정답 확정이 6건이면 0.6 | 높을수록 추가 대화 없이 안전하게 식별을 끝낸 비율이 높음 | `NEEDS_CONFIRMATION`은 최종 오답이 아니라 자동 확정 미수행으로 계산한다. 사용자 선택 뒤의 최종 Entity Accuracy와 구분한다. |
| Auto-eligible Resolution Accuracy | 사전에 ‘자동 확정 가능’으로 정한 입력 중 올바른 기업으로 자동 확정한 사례 수 / 자동 확정 가능 입력 수 | 정식 법인명 입력 8건 중 8건을 올바른 종목코드로 자동 확정하면 1.0 | exact 정규화 등 자동 확정 규칙이 명확한 입력을 놓치지 않는지 확인 | 전체 자동화 범위나 모호 입력 안전성은 측정하지 않으므로 Unsafe Selection Rate·Clarification Rate와 함께 본다. |
| Interpretation Disclosure Accuracy | 별칭·오타 정정으로 자동 확정해야 하는 사례 중, 정답 기업과 사전 정의한 해석 안내 문구를 함께 반환한 수 / 해당 사례 수 | `삼성전쟈` 5건 중 4건에서 삼성전자로 올바르게 선택하고 안내 문구까지 반환하면 0.8 | 높을수록 자동 해석이 사용자에게 투명하게 고지됨 | 수동 별칭 사전과 같은 사례로 평가하면 사전 일반화 성능이 아니라 정책 흐름의 정확성만 측정한다. |
| Candidate Recall | 정답 기업이 후보 집합에 포함된 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 10건 중 8건에서 후보 목록 어딘가에 정답 기업이 있으면 0.8 | 낮으면 이후 ranking·사용자 확인으로도 복구 불가 | 후보에 순위가 없으면 현재 `Candidate Recall`, 순위가 있으면 `Recall@K`로 기록 |
| Candidate Recall@K | 정답 기업이 상위 K개 후보 안에 있는 사례 수 / 전체 정답 사례 수 | 10건 중 7건에서 정답이 상위 3개면 Recall@3 = 0.7 | 후보를 K개만 보여 줄 UX의 상한 품질 | 후보 정렬 기준을 고정해야 함 |
| Candidate Set Size | 한 입력에서 중복 제거 후 반환한 후보 법인 수의 평균 또는 중앙값 | 20개 입력에서 후보 수 중앙값이 3개면 median Candidate Set Size = 3 | 작을수록 사용자가 고르기 쉽지만, 너무 작으면 정답 후보를 누락할 수 있음 | Candidate Recall과 함께 본다. 후보의 출처별 점수 체계가 다르면 순위 지표 대신 이 지표를 먼저 사용한다. |
| Ambiguous Candidate Recall | 의도적으로 모호한 입력에서 미리 정한 관련 기업 후보 중 실제 반환된 후보 수 / 전체 관련 후보 수 | `엘지`의 관련 후보를 LG·LG전자·LG화학 3개로 정했을 때 2개가 반환되면 2/3 | 높을수록 모호성을 하나의 법인으로 잘못 축소하지 않음 | 관련 후보 집합은 평가 전에 고정한다. 이 값만으로 최종 자동 선택 안전성을 판단하지 않는다. |
| Coverage | 자동으로 기업 하나를 확정한 양성 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 실제 기업 10건 중 4건만 자동 확정하면 0.4 | 높을수록 사용자 추가 선택이 적음 | 잘못 고른 결과를 숨길 수 있으므로 Accuracy와 함께 봄 |
| Unsafe Selection Rate | 자동 선택한 결과 중 오답 수 / 자동 선택한 전체 결과 수 | 자동 확정 5건 중 1건이 다른 회사면 0.2 | 낮을수록 안전함 | 0%라도 보류가 지나치게 많으면 Coverage가 낮을 수 있음 |
| 보류 정확도(Abstention Accuracy) | 존재하지 않거나 의도적으로 모호한 입력을 자동 선택하지 않고 보류한 수 / 보류가 정답인 사례 수 | 보류해야 할 6건을 모두 `NEEDS_CONFIRMATION`으로 보내면 1.0 | 높을수록 임의 선택을 잘 피함 | 존재하지 않는 이름, 복수 후보, 낮은 신뢰도의 유사 후보 사례가 필요 |
| Clarification Rate | 전체 입력 중 후보 목록을 제시하고 사용자 확인을 요청한 입력의 비율 | 20개 질문 중 5개에서 재질문하면 0.25 | 높으면 자동 오선택은 줄지만 대화 왕복은 늘어남 | 안전한 보류가 필요한 사례와 단순 성공 사례를 분리해 함께 해석 |
| Not-found Recall | 실제로 대상 기업이 없는 입력 중 `NOT_FOUND`로 처리한 수 / 대상 기업이 없는 전체 입력 수 | 실제 없는 입력 4개 중 3개를 `NOT_FOUND`로 보내면 0.75 | 높을수록 무관한 후보를 불필요하게 제시하지 않음 | 현재 기업코드 목록 기준의 synthetic no-match와 실제 사용자 입력을 구분해 기록 |
| False Not-found Rate | 실제 대상 기업이 있는 입력을 `NOT_FOUND`로 처리한 수 / 실제 대상 기업이 있는 전체 입력 수 | 실제 기업 표현 10개 중 1개를 못 찾았다고 하면 0.1 | 낮을수록 유효한 기업·별칭·오타를 놓치지 않음 | Candidate Recall@K와 함께 봐야 원인을 후보 생성과 cutoff 정책으로 분리할 수 있음 |
| Fuzzy-path False Not-found Rate | exact·별칭·오타 정정 경로를 타지 않고 fuzzy 후보만 사용하는 유효 입력을 `NOT_FOUND`로 처리한 수 / 해당 유효 입력 수 | fuzzy 유효 입력 4개 중 1개를 cutoff로 차단하면 0.25 | 낮을수록 cutoff가 아직 지원해야 할 미등록 오타·표현을 놓치지 않음 | 전체 False Not-found Rate는 exact·별칭 경로가 분모에 섞여 cutoff의 위험을 작게 보일 수 있으므로, cutoff 평가에서는 이 지표를 함께 기록한다. |
| Policy Preservation Accuracy | cutoff와 무관하게 처리해야 하는 exact·명시적 해석·포괄 표현 입력에서 기대 상태와 실제 상태가 완전히 같은 수 / 보호 입력 수 | exact 2건·해석 3건·재질문 2건 중 6건의 상태가 기대값과 같으면 6/7 | 높을수록 cutoff가 기존 확정·해석·보류 정책을 침범하지 않음 | 단순히 `NOT_FOUND`가 아니라고 성공으로 보지 않는다. `RESOLVED`, `RESOLVED_INTERPRETED`, `NEEDS_CONFIRMATION`을 구분한다. |
| LLM Search-term Validity | LLM이 반환한 검색어 중 정규화 exact OpenDART 기업명 인덱스에서 하나 이상의 후보를 실제로 찾은 검색어 수 / LLM이 반환한 전체 검색어 수 | 10개 제안 중 8개가 정규화 exact 후보를 만들면 0.8 | 높을수록 존재하지 않는 법인명·형식 오류 같은 무효 제안이 적음 | fuzzy 후보는 어떤 문자열에도 생길 수 있으므로 유효성 분자에 넣지 않는다. 실제 기업을 찾았다고 해서 사용자의 의도 기업이라는 뜻은 아니다. Candidate Recall과 함께 본다. |
| LLM Expansion Contribution | 기준선 후보에 없던 정답 기업을 LLM 검색어 확장 뒤 후보 집합에 새로 포함한 사례 수 / 정답 기업이 존재하는 전체 사례 수 | 기준선이 놓친 10개 중 3개를 새로 찾으면 전체 기준 기여도는 0.3 | 높을수록 LLM 호출의 실질적 후보 회수 이득이 큼 | 이미 기준선이 정답 후보를 포함한 사례는 이득으로 세지 않는다. |
| Structured-output Success Rate | LLM 호출 중 Pydantic 스키마 파싱과 필드 검증에 성공한 호출 수 / 전체 LLM 호출 수 | 20번 중 19번이 유효한 구조로 반환되면 0.95 | 높을수록 후속 코드가 안정적으로 결과를 읽음 | 유효 JSON처럼 보여도 스키마를 통과하지 못하면 실패다. 빈 검색어 목록은 형식 성공이지만 후보 품질은 별도 평가한다. |
| LLM Call Rate | 전체 입력 중 LLM 검색어 확장 경로를 호출한 입력의 비율 | 30개 입력 중 12개가 LLM 호출이면 0.4 | 낮을수록 비용·지연은 줄어듦 | 정확한 고유 exact 입력은 호출하지 않는 정책인지 함께 기록한다. 품질이 명확히 열등하지 않은 후보 간 비용 지표다. |
| No-target LLM Candidate Injection Rate | 실제 대상 기업이 없는 입력에서, LLM 제안 검색어가 OpenDART의 실제 법인 후보를 하나 이상 새로 만든 사례 수 / 대상 부재 LLM 호출 사례 수 | 존재하지 않는 5개 입력 중 2개에서 LLM이 실제 법인 후보를 만들면 0.4 | 낮을수록 존재하지 않는 질문을 그럴듯한 실제 기업으로 연결할 위험이 적음 | 기준선 fuzzy 후보가 아니라 **LLM 제안 검색어로 생긴 후보**만 센다. `NOT_FOUND` 최종 정책의 품질과는 구분한다. |

현재 `05_entity_resolution_baseline.ipynb`의 개발 결과는 별칭 규칙을 만든 사례를 다시 평가하므로 최종 성능이 아니다. 최종 비교 전에는 별칭 사전 작성에 쓰지 않은 holdout 사례가 필요하다.

## 2. OpenDART 데이터 계약과 정제

OpenDART raw 응답을 V1의 표준 재무 데이터로 안전하게 바꾸는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Field Accuracy | 정답 원천 계정·금액·통화가 맞게 매핑된 필드 수 / 검증 대상 필드 수 | 3개 기업 × 9개 항목 중 26개가 원 계정·금액까지 맞으면 26/27 | 높을수록 재무 항목 매핑이 정확함 | `account_id`, `sj_div`, 원금액을 함께 정답으로 남김 |
| Statement-Basis Accuracy | 기대된 CFS/OFS 기준을 선택한 사례 수 / 재무조회 사례 수 | CFS가 있는 8건은 CFS, 없는 2건은 OFS를 골라 10/10이면 1.0 | 높을수록 연결 우선·별도 대체 정책이 정확함 | CFS 일부 결측을 OFS 값으로 섞지 않는 정책을 별도 확인 |
| Missing-data Handling Accuracy | 결측·API 오류 사례에서 기대한 처리(결측 유지, 대체, 제한 표시)를 한 수 / 해당 사례 수 | CFS 부재 3건에서 모두 OFS 전체 대체와 기준 표시를 하면 1.0 | 높을수록 없는 값을 임의 생성하지 않음 | 단순 성공률이 아니라 오류·결측 사례가 정답셋에 있어야 함 |
| Entity Eligibility Precision / Recall | 비금융 OpenDART 공시기업을 허용·제외한 결과의 Precision/Recall | 금융 2개를 모두 제외하고 비금융 8개를 모두 허용하면 Precision·Recall 모두 1.0 | V1 대상 범위 판정 품질 | 금융·보험, 상장·비상장, 데이터 부재 사례를 포함해야 함 |

## 3. 재무 계산

원천 재무값으로 성장률, 영업이익률, ROA, ROE, 부채비율 등을 계산하는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Calculation Accuracy | 정답 수식·단위·반올림 결과와 일치한 계산 수 / 계산 사례 수 | 영업이익률 10개 중 9개가 정답 수식·반올림과 일치하면 0.9 | 높을수록 수식과 단위 처리가 정확함 | 계산 전 사용한 원천값과 수식을 함께 기록 |
| Unsafe-calculation Rate | 분모 0, 음수 자본, 결측 등 계산 불가 상황에서 부적절하게 숫자를 낸 수 / 위험 계산 사례 수 | 매출 0인 3건 중 1건에 이익률 숫자를 냈다면 1/3 | 낮을수록 안전함 | `계산 불가` 또는 주의 문구가 정답인 사례가 필요 |
| Unit Consistency Rate | 비교·계산한 값의 통화·단위가 동일하게 정규화된 사례 수 / 계산 사례 수 | 원화와 백만원을 비교 전 모두 원화로 맞춘 8/8 사례면 1.0 | 높을수록 규모 오류가 적음 | 원화, 백만원, 억원 표현과 raw 원금액을 구분 |

## 4. Router·Tool 선택·인자 생성

LLM 또는 workflow가 질문을 분석해 필요한 Tool과 인자를 선택하는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Route Exact Match | 정답 workflow 경로와 실제 경로가 완전히 같은 사례 수 / 전체 사례 수 | 재무 조회→계산이 정답인 10문항 중 8문항에서 같은 순서면 0.8 | 높을수록 분기 판단이 정확함 | 서로 다른 경로가 같은 정답을 낼 수 있으면 허용 경로를 명시 |
| Tool Precision | 호출한 Tool 중 실제로 필요한 Tool 수 / 호출한 Tool 수 | 재무·계산 2개만 필요하지만 공시 Tool까지 3개 호출하면 2/3 | 낮으면 불필요한 호출·비용이 많음 | Tool 집합 기준으로 계산 |
| Tool Recall | 정답 Tool 중 실제로 호출한 Tool 수 / 정답 Tool 수 | 재무·계산·RAG가 필요할 때 재무·계산만 호출하면 2/3 | 낮으면 필요한 조사 단계를 빠뜨림 | Tool 미호출이 최종 근거 누락으로 이어질 수 있음 |
| Tool F1 | Tool Precision과 Recall의 조화평균 | Precision 2/3, Recall 2/3이면 F1도 2/3 | 둘 사이 균형을 한 값으로 봄 | Precision·Recall을 함께 보고 해석 |
| Argument Exact Match | Tool 인자(기업, 연도, 재무제표 기준 등)가 정답과 모두 일치한 호출 수 / 평가 호출 수 | 삼성전자·2024·CFS가 모두 맞은 호출 8/10이면 0.8 | 높을수록 올바른 데이터를 조회함 | 일부 인자만 중요한 경우 필드별 정확도를 추가 기록 |
| Over-call Rate | 정답에 없는 Tool 호출 수 / 전체 Tool 호출 수 | 4번 호출 중 불필요한 웹/공시 Tool 1번이면 0.25 | 낮을수록 불필요한 조사·비용이 적음 | 필요한 재검증 호출은 오류로 취급하지 않도록 정책 명시 |
| Invalid-plan Rate | 허용하지 않은 Tool 순서, 누락 인자, 지원 밖 요청 등 실행 불가능 계획 수 / 전체 계획 수 | 20개 계획 중 기업명 없이 재무 Tool을 호출한 계획이 2개면 0.1 | 낮을수록 workflow가 안전함 | 구조화 출력 스키마 검증과 함께 사용 |

## 5. 문서 처리·Chunking·RAG

사업보고서 원문에서 근거 문단을 찾는 단계다. OpenDART 공시 목록 조회는 기간 필터 결과이므로 이 범주의 retrieval 지표를 적용하지 않는다.

### 5.1 문서 추출·OCR (필요한 경우만)

| 지표 | 의미와 계산 | 간단 예시 | 주의점 |
|---|---|---|---|
| CER (Character Error Rate) | 문자 편집 오류 수 / 정답 문자 수 | 정답 100자에서 치환 2회·누락 1회면 3/100 = 0.03 | OCR 또는 텍스트 추출 결과에 정답 원문이 있을 때만 사용 |
| WER (Word Error Rate) | 단어 삽입·삭제·치환 오류 수 / 정답 단어 수 | 정답 20어절에서 단어 2개가 틀리면 2/20 = 0.1 | 한국어 토큰화 기준을 실험마다 고정해야 함 |
| Table / Field Extraction Accuracy | 정답 표 셀·필드를 맞게 추출한 수 / 대상 셀·필드 수 | 재무 표의 30개 셀 중 28개가 맞으면 28/30 | 표 구조가 중요한 재무·공시 데이터에 사용 |

### 5.2 Chunking

Chunking 방식 자체에 모든 상황에 통용되는 단일 점수는 없다. Chunk가 달라지면 이후 retrieval·citation 품질이 달라지므로 아래처럼 평가한다.

| 지표 | 의미와 계산 | 간단 예시 | 주의점 |
|---|---|---|---|
| Gold Span Coverage | 정답 근거 구간 전체가 하나 이상의 Chunk에 보존된 사례 수 / 근거 사례 수 | 위험요인 문단 10개 중 9개가 한 Chunk 안에 온전히 남으면 0.9 | 문단·표가 부적절하게 잘렸는지 확인하는 프로젝트 정의 지표 |
| Context Preservation Rate | 필요한 제목·표 머리글·주변 문맥이 근거 Chunk에 함께 남은 사례 수 / 근거 사례 수 | 표 수치 8개 중 제목·열 머리글까지 남은 것이 6개면 0.75 | 정답 기준을 사람이 먼저 정해야 함 |
| Downstream Retrieval Quality | 동일 retriever에서 Chunk 후보별 Recall@K, MRR, nDCG@K 비교 | Chunk A의 Recall@5 0.8, Chunk B의 0.6이면 A가 검색 기회는 더 많음 | Chunking은 이 downstream 지표와 지연시간으로 최종 선택 |

### 5.3 Retrieval·Reranking

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Recall@K | 상위 K개 문서/Chunk 안에 정답 근거가 하나 이상 있는 질의 수 / 전체 질의 수 | 10개 질문 중 8개에서 정답 문단이 상위 5개면 Recall@5 = 0.8 | 낮으면 LLM이 정답 근거를 받을 기회가 없음 | K와 정답 근거 정의를 고정 |
| MRR | 각 질의의 첫 정답 근거 순위의 역수 평균 | 첫 정답 순위가 1위·2위·4위면 (1 + 1/2 + 1/4) / 3 | 첫 정답이 위에 올수록 높음 | 여러 정답이 있어도 첫 정답 순위만 반영 |
| nDCG@K | 상위 K개 결과의 등급별 관련성과 순위를 할인해 계산한 점수 | 매우 관련 높은 문단을 1위, 보조 문단을 2위에 둘수록 높아짐 | 더 관련성 높은 근거를 위에 둘수록 높음 | 0/1 또는 등급형 relevance 기준을 정해야 함 |
| Citation Retrieval Recall | 최종 답변에 필요한 각 인용 근거가 검색 결과에 포함된 비율 | 답변에 필요한 근거 4개 중 검색 결과에 3개가 있으면 0.75 | 근거 기반 답변 가능성을 측정 | 답변 단위의 필수 근거 목록이 필요 |
| Retrieval Latency | 질의부터 검색 결과 반환까지의 시간 | 같은 질문을 20번 검색한 p50이 80ms면 일반 검색 시간은 약 80ms | 낮을수록 응답성이 좋음 | 품질이 비열등한 후보 사이에서 비용과 함께 판단 |

## 6. LLM 답변·근거 검증

LLM이 Tool·RAG 결과를 바탕으로 최종 설명을 만드는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Numeric Faithfulness | 답변 속 수치·기간·계산이 Tool 원천 결과와 일치한 주장 수 / 수치 주장 수 | 답변의 수치 주장 5개 중 Tool 값과 4개가 일치하면 0.8 | 높을수록 숫자 환각이 적음 | 반올림 허용 범위를 미리 정함 |
| Citation Correctness | 답변의 인용이 실제 해당 주장을 뒷받침한 수 / 인용 수 | 인용 3개 중 2개가 바로 앞 주장 근거이면 2/3 | 높을수록 근거 연결이 정확함 | 단순 링크 존재가 아니라 주장 지원 여부를 판정 |
| Claim Support Precision | 근거로 뒷받침되는 주장 수 / 전체 검증 가능 주장 수 | 검증 가능한 주장 8개 중 6개가 문서·수치 근거로 확인되면 0.75 | 높을수록 근거 없는 설명이 적음 | 주장 단위 분할 규칙 필요 |
| Unsupported Claim Rate | 근거가 없는 주장 수 / 전체 검증 가능 주장 수 | 검증 가능한 주장 8개 중 2개가 근거 없으면 0.25 | 낮을수록 좋음 | Claim Support Precision의 보완 지표 |
| Limitation Accuracy | 데이터 부재, OFS 대체, 비교 불가 등 제한을 올바르게 밝힌 사례 수 / 제한 표시가 필요한 사례 수 | OFS 대체가 필요한 4건 중 3건에서 기준을 표시하면 0.75 | 높을수록 과장·오해가 줄어듦 | 금융 분석에서는 특히 중요 |

## 7. Agent Workflow·통합 품질

검증된 Tool·RAG·Validator를 연결한 뒤 전체 요청을 처리하는 단계다.

| 지표 | 의미와 계산 | 간단 예시 | 높거나 낮을 때의 해석 | 주의점 |
|---|---|---|---|---|
| Task Completion Rate | 최종 답변이 요청한 핵심 작업을 모두 마친 사례 수 / 전체 요청 수 | 재무 조회·계산·공시 확인이 필요한 10문항 중 8문항을 모두 끝내면 0.8 | 높을수록 사용자 요청을 끝까지 처리함 | 단순 답변 생성이 아니라 필요한 조사·계산 완료가 기준 |
| Evidence-complete Task Rate | 핵심 결론과 수치에 필요한 출처·근거가 모두 있는 완료 사례 수 / 전체 요청 수 | 완료 8건 중 근거까지 완전한 것이 6건이면 전체 기준 0.6 | 높을수록 evidence-first 원칙을 만족 | Completion Rate와 별도로 봄 |
| E2E Error / Partial-result Rate | 오류 또는 필수 결과 누락으로 부분 처리된 요청 수 / 전체 요청 수 | 20개 요청 중 API 실패·필수 근거 누락이 3건이면 0.15 | 낮을수록 안정적 | 오류, 사용자 확인 요청, 정상적인 제한 응답을 구분 |
| Agent Steps | 요청 한 건에서 실행한 node·Tool 호출 단계 수 | 재무 Tool→계산 Tool→답변 Node면 3단계 | 불필요하게 높으면 지연·비용 증가 가능 | 품질이 같은 후보 사이에서만 단순화 근거로 사용 |

## 8. 운영 성능·자원 사용

품질이 명확히 열등하지 않은 후보 사이에서 비용과 운영 적합성을 비교하는 지표다.

| 지표 | 의미와 계산 | 간단 예시 | 주의점 |
|---|---|---|---|
| p50 Latency | 전체 요청 시간의 중앙값 | 20회 요청 시간의 가운데 값이 1.2초면 p50 = 1.2초 | 일반적인 사용자 체감 속도 |
| p95 Latency | 전체 요청 중 느린 5%를 제외한 상위 지연시간 경계 | 20회 중 19번째로 빠른 요청이 3.8초면 p95는 약 3.8초 | 느린 사례·외부 API 지연을 확인 |
| Cold Start Time | 모델·인덱스·데이터를 처음 로드해 첫 요청을 처리할 때까지 시간 | 서버 시작 뒤 첫 질문까지 18초가 걸리면 18초 | 로컬 모델·대시보드 운영에서 중요 |
| Warm Latency | 초기 로드 후 반복 요청 처리 시간 | 모델을 올린 뒤 같은 유형 요청 p50이 2.1초 | Cold Start와 분리 기록 |
| Error Rate | 오류 응답 수 / 전체 요청 수 | 100회 요청 중 timeout·API 오류가 3회면 0.03 | timeout, API 오류, 파싱 오류를 원인별 기록 |
| Tool-call Count | 요청당 Tool 호출 수 | 재무 조회 1회와 계산 1회면 요청당 2회 | 불필요한 호출은 비용·지연 증가 요인 |
| VRAM / RAM Peak | 실행 중 최대 GPU·메모리 사용량 | Qwen 실행 중 VRAM 18GB, RAM 9GB까지 쓰면 그 값을 기록 | 로컬 Qwen 모델과 RAG 인덱스 운영 가능성 판단 |
| Model / Index Size | 모델 파일·벡터 인덱스 등 저장공간 | 모델 16GB와 인덱스 2GB면 총 저장공간 약 18GB | 배포와 로딩 비용 판단 |

## 갱신 규칙

- 새 지표를 사용하기 전: 이 문서에 지표의 평가 대상, 분모·분자, 정답 단위, 해석 주의점을 추가한다.
- 실제 A/B 결과가 나온 뒤: `docs/<version>/reports/`에 데이터 기준일, 후보, 설정, 결과, 해석, 채택·보류 이유를 기록한다.
- 지표 이름은 같아도 정답 기준이나 분모가 달라지면 별도 실험으로 기록한다.
